动态申请的资源需要手动释放
容易出现内存泄漏、重复释放、野指针、异常安全问题

RAII（resource acquisition is initialization）
资源的获取与对象生命周期绑定
资源的生命周期绑定到对象生命周期 ，对象析构时自动释放资源
智能指针是RAII的典型应用

智能指针本质上就是：
对象销毁时自动释放资源

shared_ptr
作用：多个对象共同拥有同一块资源
当最后一个shared_ptr销毁时，资源自动释放

内部维护引用计数，use_count，记录当前有多少个shared_ptr指向同一个资源

底层原理：
shared_ptr对象 + 控制块
```
shared_ptr

控制块中保存：
	引用计数
	弱引用计数
	删除器
	资源指针
```

需要控制块的原因
```
因为多个 shared_ptr 需要共享同一份引用计数信息。
如果把引用计数放在 shared_ptr 对象内部，每个 shared_ptr 都会有自己的计数副本，无法保持一致。
因此标准库把强引用计数、弱引用计数、删除器以及对象地址统一放到 Control Block 中，所有指向同一对象的 shared_ptr 和 weak_ptr 共同关联这一个控制块。
控制块的本质就是 把共享状态集中管理
```

shared_ptr的底层结构图
```c++
shared_ptr<int> sp1(new int(100));
shared_ptr<int> sp2 = sp1;
```

shared_ptr循环引用问题
```C++
class B;

class A
{
public:
    shared_ptr<B> pb;
};

class B
{
public:
    shared_ptr<A> pa;
};

shared_ptr<A> pa(new A);
shared_ptr<B> pb(new B);

pa->pb = pb;
pb->pa = pa;
```

```
此时A的引用计数为 2
B的引用计数为 2

当退出作用域时
pa析构，A的引用计数为1
pb析构，B的引用计数为1
永远无法变成0，造成内存泄漏
```

weak_ptr解决循环引用
弱引用，不增加引用计数

```c++
class B;

class A
{
public:
    shared_ptr<B> pb;
};

class B
{
public:
    weak_ptr<A> pa;
};
```

```c++
shared_ptr<A> pa(new A);
shared_ptr<B> pb(new B);

pa->pb = pb;
pb->pa = pa;
```

```
A count = 1
B count = 2
```

离开作用域之后
```
pa析构
A count=0
释放A

pb析构
B count=0
释放B
```

shared_ptr引用计数放在哪里？
```
shared_ptr 采用控制块（Control Block）管理资源。
每个 shared_ptr 对象内部保存资源指针和控制块指针，多个 shared_ptr 共享同一个控制块。
控制块中保存强引用计数、弱引用计数、删除器等信息。
当强引用计数减为 0 时释放对象，当强引用计数和弱引用计数都为 0 时释放控制块。
```


`shared_ptr<int> sp{new int(100)};`
与
`auto sp = make_shared<int>(100);`
堆分配底层需要
	找空闲内存、维护内存链表、加锁、更新元数据
消耗大，所以越少次数堆分配越好

```c++
shared_ptr<int> sp(new int(100));
//需要两次堆分配

//第一步
先申请对象 int 100;
//第二步
shared_ptr<int> sp(p);
//需要管理对象，申请控制块Control Block
```

```
堆
+---------+
| int 100 |
+---------+
+----------------+
| Control Block  |
| count = 1      |
+----------------+
```

```
auto sp = make_shared<int>(100);
只申请一次堆内存
要同时创建 Object 和 ControlBlock

于是直接申请一大块连续内存：
+------------------------+
| ControlBlock           |
| count = 1              |
| weak_count = 0         |
|------------------------|
| int 100                |
+------------------------+
控制块与对象连续存放，CPU缓存利用率更高
```

异常安全问题
```c++
func(shared_ptr<int>(new int(100)), foo());

//假设编译器先执行new int(100),还没来得及构造shared_ptr，这时候执行foo()，突然抛出异常，那么申请的int对象就无人接管，造成内存泄漏
```

```c++
func(make_shared<int>(100), foo());
//对象和控制块一起构造，一旦构造成功就会立即拥有资源，不会出现内存泄漏的问题
```

```c++
shared_ptr<BigObject> sp = make_shared<BigObject>();
weak_ptr<BigObject> wp = sp;

//如果sp全部销毁，但wp还存在，控制块就不能释放
//make_ptr把控制块和对象放在同一块内存中，这块内存也要继续保留到最后，直到最后一个weak_ptr被销毁
```

对于特别大的对象且会长期存在weak_ptr的场景反而会选择
```c++
shared_ptr<BigObject> sp(new BigObject);
```

`weak_ptr` 不拥有资源，不能直接解引用。不能直接访问对象
通常通过 `lock()` 获取一个临时的 `shared_ptr` 来访问对象；如果对象已经被释放，`lock()` 返回空的 `shared_ptr`。
`expired()` 用于判断对象是否已经失效，但实际开发中更推荐直接使用 `lock()` 的返回值进行判断。
```c++
if(!wp.expired())
{
    auto sp = wp.lock();
}
//if(!wp.expired())  与  wp.lock(); 之间可能发生线程切换
```

```c++
//更推荐使用这个来检查对象是否还活着
if(auto sp = wp.lock())
{
}
```


shared_ptr通常既保存对象指针，也保存控制块指针
```c++
template<class T>
class shared_ptr
{
private:
    T* _ptr;                // 对象地址
    ControlBlock* _cb;      // 控制块地址
};
```

为什么shared_ptr内有对象指针，控制块内也有对象指针？
1、提高访问效率
2、支持别名构造
```
从功能上讲，仅保存控制块指针也能找到对象。
但标准库通常让 shared_ptr 同时保存对象指针和控制块指针。
一方面这样可以减少一次间接寻址，提高 operator*、operator-> 等常用操作的访问效率；
另一方面是为了支持 aliasing constructor 等高级特性，使 shared_ptr 所指向的对象地址与控制块实际管理的对象地址可以不同，但仍共享同一个引用计数控制块。
```

##### 别名构造aliasing constructor：

普通 shared_ptr
例如：
```c++
struct Person
{
    std::string name;
    int age;
};

auto sp = std::make_shared<Person>();
```
此时：
```
sp
 │
 ▼
Person
 ├── name
 └── age
```
很正常

**现在我想只拿 age**
例如：
```
int* pAge = &sp->age;
```
这样当然可以
```
sp ------> Person
             |
             +---- age
                    ^
                    |
                  pAge
```

但是这里有个问题：
如果：
```
sp.reset();
```
Person 被释放：
```
Person  × 已销毁
```

那么：
```
pAge
```
变成野指针。
**aliasing constructor 登场**
写法：
```c++
std::shared_ptr<int> agePtr(sp, &sp->age);
```

注意：
这里有两个参数。
第一个参数：
```
sp
```
表示：
```
共享sp的控制块
```
第二个参数：
```
&sp->age
```
表示：
```
我实际想访问的是 age
```
此时关系变成：

```
          ControlBlock(count=2)
                 |
                 ▼
              Person
             /      \
          name      age
                     ▲
                     |
                 agePtr
```
关键来了
此时：
```
*agePtr
```
访问的是：
```
sp->age
```
即：
```
int
```
而不是整个 Person。

但是：
```
agePtr
```
仍然参与 Person 的引用计数。
因此：
```
sp.reset();
```
之后
```
sp销毁count:2 -> 1
```
Person 不会释放。
因为：
```
agePtr
```
还活着
直到：
```
agePtr.reset();
```
计数变成：

```
1 -> 0
```

Person 才真正释放。

 **一个完整例子**

```c++
#include <iostream>
#include <memory>

using namespace std;

struct Person
{
    string name;
    int age;
};

int main()
{
    auto sp = make_shared<Person>();

    sp->name = "Tom";
    sp->age = 18;

    shared_ptr<int> agePtr(sp, &sp->age);

    sp.reset();

    cout << *agePtr << endl;
}
```

输出：

```
18
```

为什么还能输出？
因为：
```
sp没了但是agePtr还在引用计数仍然为1
```
Person 还没释放

**那为什么这能说明 shared_ptr 需要保存 _ptr？**

看这里：
对于普通 shared_ptr：
```
控制块管理 Personshared_ptr访问 Person
```
二者一致。


而 aliasing constructor：
```
shared_ptr<int> agePtr(sp, &sp->age);
```

出现了：
```
控制块管理：    Personshared_ptr访问：    age
```
已经不是同一个地址了。

如果 shared_ptr 内部只有：
```
ControlBlock* _cb;
```
那么：
```
operator*()
```
永远只能找到：
```
Person
```

找不到：
```
age
```

所以必须额外保存：
```
T* _ptr;
```

```
agePtr_ptr ----> age
_cb -----> Person对应的控制块
```

这样：
```
*agePtr
```
访问的是：
```
age
```
而引用计数管理的仍然是：

```
Person
```

理解到下面这张图就足够应付绝大多数面试：

```
shared_ptr内部

+----------------+
| T* _ptr        | ---> Object
| ControlBlock*  |
+----------------+
         |
         v
   ControlBlock
   ----------------
   shared_count
   weak_count
   deleter
   ----------------
         |
         v
       Object
```

面试官如果问：

> 控制块已经能找到对象了，为啥 shared_ptr 还存一个对象指针？

你回答：

> 为了提高访问效率，避免每次访问对象都要先通过控制块间接寻址。标准库实现中 shared_ptr 通常同时保存对象指针和控制块指针。
